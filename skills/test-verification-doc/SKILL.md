# 测试验证文档生成器

生成可执行、可复核、结论有边界的测试验证文档。用例须说明验证什么、如何验证、如何判定及证据存放位置；结果必须来自实际记录，不以完整模板掩盖未执行项。

## 1. 确认交付模式与范围

按请求选择一种或组合，避免每次强制生成全部文档：

- **测试计划**：范围、目标、方法、环境、优先级、准入/退出、资源与风险；不填写虚构执行结果。
- **用例/执行规程**：前提、输入、准确步骤/命令、预期与断言、证据、退出及清理，具备可复现性。
- **验证报告**：整理已发生的运行记录，记录实际结果、证据、失败与限制；没有记录时只能生成待执行部分或报告骨架。
- **评审**：指出已有文档的可执行性、覆盖、判定或证据缺口，默认直接回答，不擅自落盘。

路径与命名优先遵循项目；无约定时综合文档默认 `docs/Software_Test_Verification.md`。用户只需单独计划或报告时按其目的命名，不重复创建综合文档。已有对应文档先读后增量更新，保留有效用例 ID、记录、锚点及用户内容。

默认只读取项目和资料、修改目标文档。生成文档不授权执行测试、写测试程序、修改源码/配置/构建、部署或操作硬件。用户明确要求运行或补测试时，按对应授权处理并注明额外改动，不自动 commit/push；推送由用户自行完成。

## 2. 核对基线与资料

从已提供上下文和可见文件获取必要信息，未知处写“未确认”，不因缺少环境就捏造命令或结果。

| 内容 | 依据与边界 |
| --- | --- |
| 源码与工作区 | 根目录、Git 修订、相关未提交改动、软件/内核版本、实际分析范围 |
| 目标构建 | 架构、工具链、构建目标、实际配置/Kconfig/宏、构建产物与匹配关系 |
| 目标环境 | OS、板卡/芯片、固件/设备树、外设、权限、网络与服务依赖；不以分析主机替代产品环境 |
| 需求/设计 | SRS、SAD、SDD、协议、接口或用户验收目标；核对其版本和适用配置 |
| 测试资产 | 既有框架、脚本、Makefile/CI 目标、README、测试数据、fixtures 和清理机制 |
| 执行证据 | 原始日志、命令、退出码、断言/报告、时间、环境、运行次数、已有缺陷与复测记录 |

先用限定范围的文件清单和 `rg` 检索，再读取相关入口/脚本/源码上下文。不能仅凭目标名编写构建命令，不能将搜索命中当作已验证用例。

已有 `kernel-source-analysis`、SAD/SDD 或 Bug 分析结果可按需复用；先核对源码修订、工作区、配置和范围，不把推断升级为事实，不强制调用或委派其他 Skill。

## 3. 区分需求、实现与验证证据

- **需求/验收依据**：来自明确需求、接口契约、标准或用户目标，标明来源。源码现状可以解释如何观测，不自动成为期望正确性的唯一标准。
- **实现事实**：引用真实 `相对路径:行号范围`、符号和配置条件，说明用例实际触达的接口、状态或路径。不能把未读取行号编成证据。
- **预期结果**：执行前可检验的输出、状态、错误码、时限/阈值或资源条件；不能为迎合运行结果事后改判据。
- **实际结果**：来自具体运行，保留日志/报告位置、命令、时间和环境。第三方/用户提供的记录标明来源，不声称本会话亲自执行。
- **推断/待确认**：证据不足、需求不明确、目标环境未知或命令尚待核对时明确标记；候选测试步骤不能伪装成已验证规程。

有 SRS 使用其真实需求 ID；无 SRS 时可使用测试 ID 和“观察功能/验证目标”索引，不杜撰正式需求或验收批准。设计与实现不一致时先列差异及其对判定的影响，不能选择性忽略。

## 4. 建立测试范围与用例

按实际接口、状态、风险和需求选择测试层级：静态/格式、构建、单元、集成、系统、目标板、性能/稳定性或回归。不是所有项目都需要全部层级，不用数量替代覆盖质量。

对相关内容设计正常路径、边界/非法输入、部分失败、异常传播、状态变化、并发、取消/退出及资源清理。只覆盖确实存在的机制；没有故障注入设施时写验证缺口，不编造可执行失败注入。

每个正式用例至少具有：

- 稳定 `TC-xxx`、验证目标、需求/接口/缺陷关联及适用配置。
- 前置条件、依赖和权限，测试数据与初始状态。
- 按顺序列步骤、工作目录、命令、必要参数和等待/超时；路径和目标来自项目依据。未知参数显式待确认，含占位符的命令不可标为可直接执行。
- 可观察的预期、真实断言和退出状态；单纯出现 PASS 文本或进程退出 0 不证明所有验证目标通过，需检查框架/脚本实际判定逻辑。
- 证据采集位置和方式，停止/取消、异常处理及清理步骤。
- 限制、潜在副作用及需要额外授权的操作。

性能阈值、容差、重复次数、负载和时间上限来自需求/已确认基准；没有依据时可提出“建议判据，待批准”，不能据此宣称正式验收通过。非确定性用例记录采样方法与波动，不以一次成功代替稳定性证明。

## 5. 执行规程与安全清理

文档中区分准备、构建、执行、采集、判断和清理，给出可重跑所需的配置/数据及恢复初始状态方法。不引用会自动推送/发布的包装目标来执行本地验证。

- 内核/驱动项目注明源码/运行内核/模块匹配、ARCH、设备树、板卡、设备节点和实际权限，区分宿主检查与目标板验证。
- 涉及装卸模块、设备解绑、写寄存器、改 sysctl、重启、故障注入、擦写存储、压力或网络干扰时说明对象、影响、范围、停止及恢复条件；文档列出步骤不等于允许执行。
- 获准运行时仅执行授权范围内的规程，出现非预期故障或达到停止条件即停，不无限重试或重复触发崩溃。
- 清理本次创建的进程/模块/文件/设备占用，考虑失败路径；不得删除用户原有产物或停止原有服务。资源与恢复方式无法确认时列为运行前提缺口。
- 命令失败要保留退出码；管道、日志重定向或框架统计不能遮蔽真正失败。不改断言、吞错、清空日志或只打印 PASS 来伪造成功。

## 6. 状态、结果与统计

优先遵循项目测试框架协议，同时保留其原始状态、退出码和到文档状态的映射，不自行强制统一退出码。

| 状态 | 含义 |
| --- | --- |
| PASS | 对应运行的必要断言和判据有证据表明满足 |
| FAIL | 实际断言或验收判据未满足，保留观察，不直接断定产品缺陷 |
| ERROR | 执行、工具或环境错误使测试未能有效完成 |
| SKIP | 明确前提不满足，按框架/计划规则跳过并说明理由 |
| NOT RUN | 未执行或仅计划执行，不能算作通过 |
| 待判定 | 有运行记录但缺少判据、环境匹配或足够证据，无法可靠判定 |

FAIL 可来自产品、用例/脚本、环境或前提错误，先记录事实与候选原因，不把每个失败定性为产品 Bug。ERROR、SKIP、NOT RUN、待判定均不得计入 PASS。

- 每次运行使用 `RUN-xxx` 或原框架运行 ID，保留重试与历史失败，不能以最后一次通过覆盖先前记录；间歇失败单独可见。
- 分开报告用例数、执行次数、状态分布、配置矩阵及覆盖率。统计说明分母：例如总计划用例和已完成可判定运行不同，不能混算通过率。
- 源码行覆盖只来自实际覆盖工具记录；需求覆盖、用例设计覆盖、执行覆盖和代码覆盖分别说明，建立追踪表不代表完成验证。
- 结论限定到实际基线、环境、用例和运行条件。构建成功不等于功能通过，宿主 PASS 不等于目标板 PASS，静态路径确认不等于动态覆盖。

## 7. 写作、复核与交付

创建、更新或完整性评审时按需读取 [文档与表格模板](references/document-template.md)，复用项目模板并按交付模式裁剪；无记录时不用完整结果表营造“已测试”的外观。

交付前核对：

- 目标、基线、配置、环境、范围和不覆盖内容明确，资料版本匹配或差异可见。
- 用例有可执行前提、准确步骤、可观察判据、证据和清理；未知命令/阈值标为待确认。
- 预期、实际、第三方记录、本会话操作及未执行事项分开，所有 PASS 有足够证据。
- 需求/设计/实现/测试/运行结果追踪一致，统计口径可复核，重试和失败未隐藏。
- 引用路径、源码行号、日志位置、链接、表格和 Markdown 围栏已核对；证据缺失不伪造附件。
- 文档 Diff 仅含授权内容，未越权修改实现/测试或操作目标系统；没有声称未执行的构建、测试或发布成功。

最终给出文档路径（评审则给意见）、交付模式、覆盖范围、实际文档检查及缺口。明确本次是否运行测试；只生成文档时直接说明“未执行测试”。

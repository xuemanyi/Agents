# Linux 内核 Bug 分析

以可核查证据解释故障，而非从堆栈或 API 名称猜结论。默认进行离线、只读分析，交付故障定位、候选假设、根因证据及最小修复/验证方案。

## 1. 模式与权限边界

- **分析**：默认只读源码、已有日志、配置、符号和转储，不修改源码/配置/测试，不为定位自动运行目标、安装依赖或操作设备。用户仅要求分析时给修复建议，不直接打补丁。
- **修复**：用户明确要求修复时，可在授权范围作最小修改，并执行权限允许、风险可控的验证。先查适用项目规范及用户已有改动，保护 API/ABI、并发语义和无关内容。
- **复现/诊断**：已有日志能推进时优先离线分析。运行复现、加载/卸载模块、解绑设备、修改 sysctl/追踪配置、启用故障注入、压力测试、重启或采集转储须有相应明确授权；工具可调用不等于已授权。
- 不执行会清空证据的操作，如清空日志；不为“确认问题”主动触发 panic、SysRq、内存/存储破坏或线上设备故障。
- 获准复现时限定环境、操作范围、资源/时长上限、停止与恢复条件；出现预定故障或非预期异常即停止，不循环触发崩溃或反复重启。
- 不自动委派。复用其他分析结果前核验基线与证据；不假定调试工具、专题 Skill、目标板或 root 权限存在。不自动 commit、push、部署或烧写；推送由用户完成。
- 默认直接回答；用户要求报告落盘时才写入指定位置或项目约定目录，不机械创建重复报告。

## 2. 建立故障与源码基线

从当前上下文和只读材料收集必要信息，缺失项标“未确认”。没有目标路径时不随意挑选磁盘中的内核树；先索取最小必要路径或文件，同时分析已提供材料。

| 基线 | 核对内容 |
| --- | --- |
| 源码 | 根目录、Git 修订、相关工作区修改、厂商补丁、内核版本及目标范围 |
| 构建 | ARCH、实际 `.config`、重要宏、工具链、优化/LTO、目标构建及已有构建记录 |
| 运行 | 故障系统版本、硬件/设备树/固件、启动参数、模块及其版本、相关 taint 状态（如有） |
| 故障 | 预期/实际、首次出现时间、触发步骤、频率、工作负载、是否回归及最近已知正常版本 |
| 证据 | 原始日志前后文、CPU/任务/时间、检测器报告、寄存器、堆栈、已有 vmcore 和符号产物 |

- 运行版本不能代替源码版本。相同版本字符串不证明同一次构建；确认 `vmlinux`、模块、调试信息、System.map 和转储/日志匹配，能取得构建 ID 时核对。
- defconfig 不是实际配置。PREEMPT/RT、SMP、架构和诊断选项未知时，不把对应上下文/锁语义当作确定前提。
- 区分原始故障与之后的连锁 WARN/Oops/panic；先找最早有效异常及其上下文，检测器/报错函数不一定是破坏发生位置。
- 保留原始日志的时间、CPU、PID、模块和偏移；展示时避免泄露凭据或无关内存内容，不改写证据来迎合假设。

## 3. 证据与结论等级

为重要结论使用稳定证据 ID，如 `SRC-01`、`LOG-01`、`HYP-01`、`TEST-01`。源码引用实际读取的 `相对路径:起始行-结束行` 与符号；日志引用文件/行号或时间与片段标识，转储引用匹配产物及实际查询结果。

| 类别 | 判定要求 |
| --- | --- |
| 已观察故障 | 日志、转储或复现记录直接证明症状；不自动证明根因 |
| 源码已确认 | 代码直接证明特定操作、分支、资源或同步关系，保留配置/状态条件 |
| 候选原因/静态推断 | 有依据但触发条件、动态绑定、对象身份或因果链尚不完整；列缺口及反证方法 |
| 已证实缺陷 | 具体错误条件及违反的接口/生命周期/同步约束已被证据证明；不要求冒险运行才能确认，但纯猜测不算 |
| 已确认根因 | 已证实缺陷与本次故障之间建立完整因果联系，排除会改变结论的关键替代解释，并列依据 |
| 未确认 | 缺少匹配源码、配置、符号、运行状态或关键路径；说明影响与最小所需证据 |

“已证实代码缺陷”不一定是“本次事故根因”；根因确认也不等于修复验证完成。短期不复现、压力测试未报错或更改后症状消失，均不能单独证明竞态消除或因果成立。

若复用 `kernel-source-analysis`，核对其根目录、修订、工作区、配置和范围，保留事实 ID 及等级；该 Skill 的事实结论只是本分析的输入，不自动构成缺陷定性。

## 4. 定位与因果链

1. **归类现象**：明确是 panic/Oops/WARN、检测器事件、卡死/延迟、内存/数据异常还是功能失败。保留检测器原始分类，另列尚未证实的解释。
2. **映射位置**：先核对产物再解码 PC/指令、函数偏移、模块偏移或栈帧；对 KASLR/重定位、内联、优化和栈损坏保留边界。资料不足时不要编造精确源码行。
3. **追踪入口**：读取定义、声明、实际调用及注册/触发路径，检查构建条件。直接调用、函数指针、注册、异步调度、执行和消息传播分别标记。
4. **回溯对象**：追踪输入、长度/地址、对象身份、关键赋值、引用、共享读写、状态及错误传播，不只停在报错行。
5. **检查生命周期与同步**：沿正常、部分失败、恢复和退出路径检查分配/映射/发布、引用、异步使用、撤销/同步/释放及锁保护范围。
6. **构建假设并尝试反证**：每项假设列支持证据、触发前提、矛盾/替代解释、缺口及最小验证。不要先认定 NULL/UAF/死锁，再选择性收集证据。
7. **限定结论**：能证明多少就交付多少；日志不足时给出排序候选及依据，不虚构概率或把缺失材料视为排除证据。

分析崩溃/内存报告、并发卡死、设备/DMA 或回归时，按需读取 [专题定位要点](references/triage.md) 的相关部分；无需全量展开每个专题。

## 5. 修复方案与验证

- 将触发条件、最早错误操作、失效约束、传播路径与最终症状连接成可检验的链；每条因果边给证据和等级，缺口直接标注。
- 提出修复时说明为何能切断因果链、涉及范围、兼容性/锁序/上下文/时序影响及替代方案。禁止仅屏蔽 WARN、吞掉错误、删除功能或增加无依据延时来假装修复。
- 只有已获修复授权才改代码；考虑部分初始化失败、remove/unbind、异步取消及跨调用方影响，不为修一个路径破坏另一路径。
- 验证针对实际失效条件：可行时在可控环境比较修复前触发与修复后结果，并检查正常功能、异常/退出及相关回归。不能复现时明确采用的静态依据和未覆盖条件。
- KASAN/KCSAN/lockdep、故障注入、压力或目标板验证按证据需要提出，并说明配置/运行风险；不自动开启、重建内核或部署。
- 记录真实命令、构建/运行基线、配置、结果、次数/时长和停止条件，区分通过、失败、环境错误、前提不满足及未执行。验证失败则分析原因，不改测试来制造成功。
- 无法匹配符号、缺少硬件或权限时继续可做的静态分析，列出进一步确认所需的最小材料；不声称未知区域安全或修复已通过。

## 6. 输出与交付检查

简单疑点直接给：症状与基线、证据结论、因果/候选、建议和未确认项。复杂问题或落盘报告使用 [Bug 分析报告模板](references/bug-report.md)，按范围裁剪。

交付前确认：

- 源码、运行产物、配置和故障记录的匹配程度明确，行号/符号来自真实读取与解码。
- 堆栈位置、错误发生位置和根因没有混为一谈；间接绑定、配置和可达性条件可见。
- 相关对象正常/异常/退出及并发路径已检查，尚未展开的范围明确。
- 观察、推断、缺陷、事故根因、建议及验证状态分别表述，有替代解释和反证依据。
- 未越权操作系统/硬件或修改项目，未编造测试、运行记录、缺陷严重性或根因确认。
- 最终说明覆盖范围、主要结论、实际验证、剩余缺口及修复文件（若获授权并实际修改）。

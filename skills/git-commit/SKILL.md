# Git Commit

完成可审查、范围清晰的本地提交。**本 Skill 只执行本地 commit，绝不执行任何形式的 push；所有代码由用户自行推送。**

## 1. 授权与范围

- 用户调用本 Skill 并要求提交现有改动，或当前工作流已明确授权提交时，按范围执行，不重复索要同一授权。
- 编写、安装或讨论本 Skill，以及完成开发、修复、重构、文档或测试修改，本身不授权提交当前工作区。
- 先确认目标仓库和本次任务范围；非 Git 目录不擅自初始化仓库。范围可从会话及 Diff 明确时直接执行，存在实质歧义时先说明并询问。
- 不回退、覆盖或掺入用户无关修改，不修改 Git 全局配置、身份、远端或认证设置来强行完成提交。
- 项目提交约定优先于通用格式默认值；与用户当前明确格式要求冲突时说明差异，遵守适用指令，不私自改写项目政策。

## 2. 提交信息

默认格式：`<type>: <short description>`，使用英文、单行、无表情符号，准确描述核心改动。优先用小写动词开头的祈使表达，建议不超过 50 个字符，最多 72 个字符（包含前缀）。

| type | 用途 |
| --- | --- |
| feat | 新功能 |
| fix | 缺陷修复 |
| refactor | 不改变行为的重构 |
| docs | 文档 |
| test | 测试 |
| perf | 性能优化 |
| build | 构建系统/工具链 |
| ci | CI/CD |
| chore | 其他维护 |
| revert | 回滚 |

- 以实际 Diff 为依据选类型，不把功能变更写成 refactor，不用 `update code`、`fix issue` 等空泛摘要，也不在摘要中声称未经验证的效果。
- 默认不写正文；用户或项目要求 scope、正文、关联编号、签署或来源披露时遵循，不添加未经要求的自动生成署名，不移除要求保留的署名。
- 每个提交尽量只完成一个独立功能/修复；同一功能的代码、文档和测试可一起提交。不相关功能分开，且都必须在已授权范围内。

示例：

```text
feat: add ARM64 exception vectors
fix: handle partial socket writes
refactor: simplify memory allocator
docs: add scheduler design document
test: cover UART receive timeouts
build: add QEMU build target
```

## 3. 检查变更与验证结果

1. 在目标仓库检查 `git status --short`、`git diff`、`git diff --cached`；按需获取仓库根目录、分支、HEAD 和文件清单。
2. 读取任务相关未跟踪文件，不能只看 diffstat；区分已暂存、未暂存和用户已有修改，核实重命名、删除、二进制或子模块变化。
3. 检查冲突和未完成的 merge/rebase/cherry-pick 等操作；存在时说明具体状态，不自动续作、终止或凭猜测解决冲突。只有明确授权并正确解决后才能继续。
4. 排除无关文件、临时调试文件、密钥/凭据、构建垃圾；项目明确跟踪的必要生成物按约定处理，不因文件是生成物就擅自删除。敏感内容不得原样输出。
5. 核查与变更有关的实际验证结果，并运行权限允许且必要的项目检查。文档等低影响改动可只做相关格式/内容检查，不为提交机械运行全部测试。
6. 必要编译/测试失败时不提交为已完成功能，不修改断言制造 PASS，不用 hooks 替代必要验证。未执行的验证写明原因；环境阻塞影响验收时说明限制并在需要用户决定时询问，不宣称已通过。

## 4. 精确暂存与提交

- 明确拟提交的文件或片段，使用显式路径及安全引用；禁止无条件 `git add .`、`git add -A`、`git commit -a`，不让通配符扩大范围。
- 同一文件混有任务相关和无关改动时，按片段精确暂存；已有部分暂存内容时先核对，不能用整文件 add 破坏用户的暂存选择。
- 已暂存的无关改动不能混进提交，也不擅自取消用户暂存。无法在保留原暂存状态的前提下可靠隔离提交时，说明具体文件/片段并请求决定。
- 暂存后重新读取完整 `git diff --cached`，检查 `git diff --cached --check` 及暂存区文件清单，确认包含本次全部必要内容且没有越界。提交信息必须描述最终暂存内容。
- 没有实际差异时不创建空提交。禁止 `--allow-empty`，不为制造提交改动文件。
- 执行普通 `git commit`。禁止 `--no-verify` 或通过环境变量/配置禁用 hooks；禁止 `--amend`，除非用户明确要求修改已有提交。
- 使用结构化参数或可靠 shell 引用传递信息，不把不可信文本拼成可执行命令。项目要求多行信息时用临时文件传给 `--file`，保留真实换行。
- 若执行期间发现 HEAD/暂存区被其他进程改变，重新核对范围；不要继续提交陈旧快照。hook 失败或改写文件时检查新状态，仅在任务范围内修复并重新验证，不盲目重试。

## 5. 推送禁令

- **绝不执行 `git push`，包括普通推送、首次推送、`--all`、tags、mirror 和任何强推。所有远端推送均由用户手动完成。**
- 不使用脚本、alias、Makefile、hook、插件或其他命令间接触发 push，不自动创建远端 PR、发布或部署。
- 若有证据表明提交 hook 或项目包装命令会推送/发布，先说明该副作用并停止该路径；不得以 `--no-verify` 绕过 hook，也不得为了完成本地提交擅自修改 hook。
- 本 Skill 不包含推送步骤，不把“本地提交完成”表述为“已同步远端”，不因用户要求提交所有改动而理解为允许推送。

## 6. 核验与交付

- 提交成功后核对新 HEAD、提交内容、实际 subject 和 `git status --short`，确认提交只含授权内容；若有多个提交逐一报告。
- 不因命令返回部分输出就宣称成功。若 hook 后置步骤等导致返回异常，读取 HEAD 与状态确认是否实际产生提交，避免重复提交；说明残余问题。
- 本地提交成功但工作区仍有改动时说明剩余项，不声称工作区干净；不要为了清空状态提交或删除它们。

成功输出：

```text
Commit: <short-hash>
Message: <type>: <short description>
Status: committed
Push: not performed (user will push manually)
```

按需补充实际验证及剩余改动。没有变更时报告 `Status: no changes`；失败时报告具体原因及当前状态，不能输出 `Status: committed`。若已产生提交但后续检查失败，分别说明已产生的 hash 和未完成的核验，不伪报全部成功。

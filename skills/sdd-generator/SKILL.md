# Software Detailed Design（SDD）生成器

可追溯地解释真实实现及边界条件，而非逐行复述源码。SAD 描述系统组件与协作，SDD 深入组件内部；通过既有模块/接口 ID 和交叉引用衔接，不复制整篇 SAD。

## 交付与操作边界

- 识别新建、更新或审查。默认只读取项目并创建/更新目标 `Software_Detailed_Design.md`，路径、命名及结构遵循项目约定；仅审查时直接回答，不擅自落盘。
- 已有 SDD 时先阅读并增量维护，保留有效内容、用户修改、锚点和 ID，修订因实现变化失效的结论及关联证据，避免重复文档和无关重写。
- 不修改源码、测试、构建或部署配置；不为写文档自动编译、执行目标、加载模块或操作硬件。确需扩大范围/权限时说明具体需要并确认，不重复询问已授权的文档操作。
- 分开表述源码事实、条件确认、静态推断、待确认项、质量候选问题及建议。没有证据不声称缺陷成立，也不声称测试通过。
- 不自动委派或假定其他 Skill 可用。正式缺陷审查属于其他任务；可保留后续审查入口，不在本 Skill 中扩展为缺陷报告或自动修改实现。

## 1. 确立基线并核验已有设计

记录项目根目录、Git 修订/工作区变更、软件或内核版本、目标架构/平台、目标构建、Kconfig/宏、目标运行环境及文档范围；未知字段明确写“未确认”，不用分析主机环境冒充产品环境。

优先按需阅读适用项目规则、README、已有 SRS/SAD、Makefile/Kbuild/CMakeLists、Kconfig、实际配置及部署脚本。核对 SRS/SAD 的源码修订、配置、范围与当前工作区，过期声明注明差异后重新核查，不照搬旧结论。

若已有 `kernel-source-analysis` 结果，仅在基线、工作区内容、配置及范围一致时复用证据；缺口或过期部分补查。保留其证据等级与成立条件，不能把静态推断升级为事实。没有该结果时直接只读分析，不强制依赖另一个 Skill。

## 2. 分层扫描与覆盖台账

1. **文件普查**：用 `rg --files` 等列出范围内实现、头文件、汇编、相关生成接口和脚本；按需检查被忽略但实际存在的配置/生成物。建立模块归属、构建参与状态和排除理由。
2. **构建追踪**：从目标构建、依赖、配置与条件编译确定实际编译单元，区分必选、条件可选、未参与和未确认；目录存在、包含头文件不等于已编译链接。
3. **逐文件梳理**：相关实现文件确认职责、导出接口、重要全局/static 状态和公开/内部函数清单。头文件定位类型、ABI、宏和声明，不默认其为独立实现模块。
4. **关键函数深入**：优先入口、状态转换、资源获取/释放、同步、异常处理、跨模块接口和复杂业务函数；getter/setter、薄包装及纯转发函数可合并索引。
5. **覆盖核对**：记录清单口径、总数、已检查、待检查、未参与构建及外部/生成源码。文件名检索、读过部分代码、已逐文件梳理和关键路径深入是不同覆盖层级，不混为逐行阅读。

完整 SDD 尽可能覆盖目标构建相关源码，不机械复述全部函数。大型仓库可分批并保留覆盖清单；第三方、生成物和其他架构分支按理由排除。统计项若存在重叠说明口径，不提供无法复核的覆盖率。

## 3. 证据与追踪规则

核心结论引用实际读取的 `相对路径:起始行-结束行`、关键符号和条件。缺少行号时先补查，仍无法取得则写“位置待定位”，不编造数字。

| 等级 | 使用标准 |
| --- | --- |
| 源码已确认 | 定义、赋值、分支或调用路径直接支持结论 |
| 条件成立时确认 | 在明确 Kconfig、架构、宏、构建或运行分支条件下直接支持；说明条件是否已确认满足 |
| 静态推断 | 有代码依据但缺少完整动态绑定、状态或调用方证据；列依据与缺口 |
| 代码中未确认 | 文件、外部实现、配置、调用方或运行时信息不足 |
| 文档声明，代码未确认 | SRS/SAD 等资料声明但未获当前实现证据；引用文档位置 |

- 名称、注释和通用 API 习惯仅提供线索，不能证明项目结果；“未检索到”须限定范围，不等于不存在。
- 直接调用、函数指针、回调注册、调度、异步执行和 IPC/消息传播分别记录。间接调用追踪声明、赋值、覆盖和调用点；多目标列候选与条件，可能可达不等于必然执行。
- 编译链接、注册成功、运行时绑定和实际执行分别表述。宏/内联、弱符号、条件编译、动态装配和架构分支保留条件与证据边界。
- 使用稳定的 `FILE-xx`、`FUNC-xx`、`DATA-xx`、`FLOW-xx`，与 SAD 既有 `MOD-xx`、`IF-xx` 对齐；保留旧 ID，避免无关重编号或混淆不同文档中的同名流程 ID。
- 有 SRS 时追踪：**真实需求 ID → SAD 模块/接口 → 源文件 → 函数/关键语句 → 验证证据（如有）**。缺少 SAD 时相应关系标未建立，不虚构正式模块 ID。没有 SRS 时建立“观察到的功能 → 实现”索引，不杜撰需求编号或验收状态。
- 工作区变更属于基线，不能写成已提交内容；分析期间内容变化时重查相关引用和结论。

## 4. 逐文件事实卡

每个目标实现文件至少给精简记录；纯声明、宏或薄包装文件可压缩，避免相同背景段落。卡片字段为：

- **文件与模块**：相对路径、FILE-ID、所属 MOD-ID（如有）、编译参与条件。
- **职责**：真实输入/输出和对外提供的能力，已有 SAD 总览仅交叉引用。
- **依赖**：分别列头文件/声明、编译链接、调用和运行时绑定依赖。
- **数据**：关键类型、全局/static 对象、所有权与可见性；指向 DATA-ID。
- **接口/函数**：公开与内部函数索引；关键函数指向 FUNC-ID 详解，简单函数简述。
- **生命周期**：初始化、运行、错误与清理入口及证据。
- **并发/异常**：实际上下文、同步操作、共享状态、关键错误路径和未确认项。

## 5. 关键函数详细设计

按复杂性、资源/并发约束及架构重要性选取，不要求每个函数使用九项长文。每个关键函数按相关性记录：

1. **定位与原型**：真实定义/声明、行号、编译条件和可见性。
2. **契约**：输入/输出、返回值与错误码、前后置条件、NULL 约束、参数所有权；未经源码支持的约束不自行补充。
3. **步骤与状态**：分支、循环、转换、关键读写和同步点，保留短路、提前返回和异常路径。
4. **关系**：已见上层调用者、直接调用、间接绑定、注册者和异步触发者，附位置与条件，不声称全局穷尽。
5. **资源**：分配/借用、引用计数、映射、复制/共享、所有权转移与释放。
6. **错误**：失败前提、清理/回退、传播、代码存在的重试与恢复。
7. **上下文/并发**：入口证据、进程/IRQ/workqueue/线程上下文、睡眠约束、保护对象与共享访问来源。
8. **底层机制**：仅解释函数实际使用且影响设计的 Linux/POSIX 行为，区分 API 语义和当前实现处理。
9. **证据/限制**：位置、配置、未展开层次和未确认项。

已有匹配版本的函数分析文档时可引用并补充 SDD 所需关联，避免重复全文。

## 6. 核心路径、数据与资源生命周期

按工程实际选择启动/main/module_init/probe/注册入口、初始化与部分失败回退、业务/事件/消息、异步回调、状态迁移、线程或 IPC 协作、错误传播、停止与卸载。不存在或未知的路径如实说明，不制造统一主循环或线程退出链。

每条 FLOW 记录触发入口、关系类型、前提、关键函数、输入/输出、状态、错误返回与资源变化。多层封装展示关键节点和可展开证据，不无限列出所有辅助函数。

对实际使用的 ABI、共享内存、struct/enum、全局/static 对象、缓冲区、队列/链表、FD、锁、work/timer、映射和 DMA 等，追踪：

**定义/布局 → 初始化/获取 → 发布/使用 → 并发访问 → 异常处理 → 撤销发布/释放**。

注明所有权、持有者、引用计数、有效期、清理责任和上下文。区分别名、共享与深拷贝；不能仅凭指针传递推断所有权转移，也不能仅凭 free/close 存在推断全部路径均释放。分别分析 devm、显式管理、异步取消/同步、用户态资源和目标版本差异。

## 7. Linux/POSIX 接口与系统调用边界

只对实际使用且影响实现的 API 深入，按三层区分：

1. **项目调用契约**：实际参数、返回值处理、重试/停止逻辑、源码位置。
2. **OS/API 语义**：需要补充时核对匹配目标版本的官方/权威资料，引用出处；不能用一般语义替代项目代码。
3. **内核内部路径**：只有匹配内核源码或明确适用的权威证据时才确认具体 syscall、VFS、Socket、Futex、调度器或驱动链；否则标未确认，不伪造精确版本调用链。

| 机制 | 关注内容 |
| --- | --- |
| read/write/ioctl/mmap | FD/设备契约、用户缓冲区、阻塞模式、返回值、映射有效期 |
| poll/select/epoll | readiness、等待/唤醒、事件模式、取消阻塞与关闭 |
| socket/IPC | 协议/消息边界、部分收发、队列/背压、连接状态与错误传播 |
| pthread/cond/mutex/semaphore | 创建/回收、等待条件、锁范围、唤醒和停止协议 |
| signal/timer | 异步信号安全、回调、取消和退出同步 |
| IRQ/workqueue/RCU/DMA | 注册/触发、睡眠限制、可见性、引用与设备边界 |

针对适用 API 检查 EINTR、EAGAIN/EWOULDBLOCK、零返回、short read/write、部分发送、超时、重启和阻塞退出。不要把所有 API 都套用 errno 或同一重试规则；注明接口实际是返回负错误、设置 errno、直接返回错误码或采用其他约定。

## 8. 图示与质量候选问题

图能明显改善理解时才用 Mermaid：`flowchart` 表达分支、循环、回退和释放；有确切时序证据时用 `sequenceDiagram`；状态集合/转换可确认时用 `stateDiagram-v2`。对象关系图不冒充运行时调用图。

图保留关键条件和异常分支，区分直接调用、注册、事件及消息，关联正文证据。复杂图分拆，不为每个函数画图；抽象 API 名称不能证明运行顺序。

质量检查围绕实际设计证据：资源配对、指针/长度校验、返回值/短读写、共享状态/锁序/引用、线程停止与唤醒、signal handler、异步引用、隐式依赖、错误码/日志契约及重复状态源。

只列有代码依据的条目：**位置 → 观察事实 → 触发前提 → 潜在影响 → 证据等级 → 建议验证/改进**。分别标记“风险候选”“设计建议”；“确认缺陷”仅引用已有充分证据及其验证范围，不把新静态疑点升级为缺陷。用户要求正式审查时作为独立任务处理，可交接可用的 code-review 能力，不在本 Skill 中自动扩展或修复。

## 9. 写作、复核与交付

写作或完整性审查时读取 [SDD 结构与记录模板](references/sdd-template.md)，优先适配项目模板。正文集中关键实现，普通函数用索引/附录；逐函数全文档只在用户明确要求时扩展。

交付前核对：

- 基线、目标构建、架构/配置及文件覆盖台账清楚；未检查与排除项可见。
- 文件索引对应目标范围，关键函数结论有实际源码位置，条件与动态绑定缺口未隐去。
- 调用、间接绑定、注册、调度、异步执行与消息语义分开；数据所有权、正常/失败/退出及并发边界均与已分析路径相符。
- SRS/SAD 关联可追溯，旧结论已核验；没有无依据需求、验收状态或内核路径。
- 图文及证据一致；候选问题、已有确认缺陷、建议严格区分。
- 检查引用文件与真实行号、表格/链接/围栏及交叉引用；可用时以现有 Mermaid 工具解析/渲染，不自动安装依赖或执行项目脚本。未渲染则明确说明。
- 复核目标文档内容和 Diff，保留既有有效内容，未改动源码、配置或测试。

最终给出文档路径（审查则给结果）、新增/更新内容、实际覆盖范围、已执行检查及待确认项。文档生成与静态核查不等于构建、测试或动态行为验证通过。

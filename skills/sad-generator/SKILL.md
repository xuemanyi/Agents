# Software Architecture Design（SAD）生成器

还原已实现架构，使读者理解系统边界、组件职责、接口依赖、关键运行路径、资源与线程模型、部署约束及结论依据。SAD 关注系统关系；函数实现细节仅在解释架构约束确有必要时展开。

## 交付与操作边界

- 先识别任务是新建、更新还是评审。新建/更新默认只读取项目并修改目标 SAD；评审只回答发现与证据，不擅自落盘。
- 默认文件名为 `Software_Architecture_Design.md`，路径和章节遵循项目约定。已有对应文档时先阅读并增量更新，保留有效内容、用户修改、锚点与追踪关系，避免重复创建或无关重写。
- 不修改功能代码、配置、构建、部署脚本或测试，不为生成 SAD 自动编译或运行目标，不执行高风险系统/硬件操作。现有授权内完成必要工作；确需扩大范围或权限时说明具体原因并确认。
- 区分已实现事实、文档中的目标/意图、静态解释、风险和建议，不把未实现意图写成当前架构，不把候选风险写成已验证缺陷。
- 不自动提交、推送或委派。其他 Skill 可用时按范围复用其证据，不假定能力存在或已被执行。

## 1. 确认基线并完成架构普查

按相关性获取并记录：源码根目录、Git 修订与工作区变更、软件/内核版本、ARCH、目标构建模式、重要配置/宏、部署环境、交付范围。缺失项写“未确认”，不能以分析主机的内核或运行环境替代产品环境。

先建立仓库文件清单与构建入口清单，再逐层追踪目标构建的模块依赖、接口、调用和装配关系：

- 阅读适用项目规则、README/CONTRIBUTING、已有架构文档；存在 `Software_Requirements_Specification.md` 或项目指定 SRS 时优先阅读相关需求。
- 用 `rg --files` 等只读方式普查文件；注意忽略规则可能隐藏已有配置/生成物，必要时限定路径检查。按需读取 Makefile/Kbuild、CMakeLists.txt、Kconfig、实际配置、启动/部署脚本、协议、测试及相关 `.c/.h/.cpp` 等实现。
- 根据编译目标和配置选择源文件，不把目录存在或头文件包含视为组件已链接/启用；区分实际配置与 defconfig 候选。
- 完整 SAD 覆盖目标构建的所有架构相关组件，第三方、生成文件、不相关平台和未启用分支可按理由排除；记录已覆盖、排除和未展开部分，不宣称未检查区域已“完整扫描”。
- 大型代码库可分批分析，但每批清楚标注实际范围和待扩展入口，最终文档保留覆盖清单。

相关工作区修改属于证据基线的一部分，不将其当作已提交内容。长任务中发现源码变化时重查受影响结论和行号。

## 2. 提取并复用可核查事实

重要结论使用以下标记，不能仅凭名称、注释或搜索匹配证明实现：

| 标记 | 含义与要求 |
| --- | --- |
| `[源码已确认]` | 源码、构建或部署配置直接支持；引用相对源码根目录的 `路径:行号` 或行号范围，并说明配置/状态条件 |
| `[文档声明，代码未确认]` | 需求/设计资料声明但实现证据不足；引用文档位置，不描述为已实现 |
| `[推断待确认]` | 根据部分源码解释架构；给出依据、缺口和可能替代解释 |
| `[建议方案]` | 面向未来的选择，与现状及原始设计意图明确分开 |

- 为关键组件、接口、流程和风险使用一致的 ID，如 `MOD-01`、`IF-03`、`FLOW-02`、`RISK-04`。项目已有 ID 时沿用，不因更新随意重编号。
- 引用必须来自实际读取的位置；无法取得行号时先补查，仍不能取得则写“位置待定位”。“未找到”只能表示已查范围未获证据，不能证明全局不存在。
- 若已有 `kernel-source-analysis` 结果，核对其源码根目录、修订、工作区变化、配置和覆盖范围后复用事实 ID；过期或缺失部分重新定位。该 Skill 的“静态推断”不能升级为 `[源码已确认]`；条件确认须保留条件。
- 复用分析结果不授权自动委派。需要时在当前会话读取可用 Skill 的要求或直接补充只读调查。
- 区分头文件依赖、编译链接依赖与运行时调用/绑定。宏、函数指针、回调、弱符号、异步和多进程装配须追踪赋值、注册/分发与条件，不仅列引用。

## 3. 建立系统级架构模型

### 系统边界与组件

识别真实的外部参与者：用户、业务应用、其他进程/服务、网络节点、OS、内核子系统、驱动、固件或硬件。说明入口/出口、传输机制、进程和信任边界。只有项目证据支持时才加入 Kernel/Driver/Hardware 节点，不强套 Application/Service/Core 层次。

依据构建单元、组件 API、运行时装配、目录和共享状态识别组件，先还原结构，再判断是否存在稳定分层。关键模块至少说明：

- ID、职责、源码边界、对外接口及依赖方向。
- 输入/输出、关键对象、所有权与跨边界契约。
- 初始化、运行、异常、退出和重启路径（不存在或未知则标注）。
- 执行上下文、共享状态、同步约束和配置条件。
- 对应需求或观察到的功能、证据、已知约束及待确认点。

“为何这样拆分”只有设计资料、提交背景或代码约束支持时才能作为既有原因陈述；否则标注推断或建议，不凭审美补出模块和分层。

### 控制流、数据流与生命周期

选择架构代表路径：启动/probe、配置装载、依赖初始化与回退；主循环、事件/业务处理；回调/IRQ/线程/work/timer/IPC；代码实际存在的错误传播、重试或降级；关闭、卸载及异步取消和资源回收。

每条路径记录：**触发者 → 执行组件 → 数据/状态变化 → 错误结果 → 所有权变化或后续事件**。区分直接调用、经函数指针调用、注册、调度、执行触发与消息传递；注册成功、运行时绑定和已实际执行不是同一事实。

数据流记录来源、格式、校验/转换、缓存、传输、消费者及生命周期。区分别名、共享、复制和所有权转移；关键对象覆盖正常及相关部分失败/退出路径。不能由 `devm_*` 或一次释放推定全部异步引用均终止。

### 并发、状态与资源

定位进程/线程、IRQ、异步工作、信号与事件循环的创建、执行和停止关系，记录锁、原子、RCU、等待/唤醒、条件变量和 IPC 的实际位置及保护范围。说明资源归属、释放顺序、join/flush/cancel 与同步边界，不凭单一路径保证全局无竞争。

有真实状态变量/枚举时追踪写入点、触发条件、异常与恢复；只有转换关系可验证时才建状态机，变量名为 `state` 不足以证明完整状态机。

### 配置、部署与运维

只记录确实存在的配置来源和覆盖顺序、日志/错误码契约、启动方式、权限/设备节点、进程布局、依赖服务、固件及发布形态。分散实现就如实说明，不虚构独立日志或配置子系统。无法从资料确认的目标环境标为未确认。

## 4. 按需解释项目使用的 Linux/POSIX 机制

仅解释实际使用且影响架构的机制，连接到使用位置，说明项目如何依赖、如何使用及约束；不写通用教科书。

| 机制 | 关注的架构约束 |
| --- | --- |
| 字符设备、ioctl、mmap | 用户/内核边界、file_operations、ABI、缓冲区/映射生命周期 |
| poll/epoll | readiness、等待/唤醒、边沿/水平触发、阻塞退出 |
| pthread、内核线程、workqueue | 创建/停止、执行上下文、共享状态、join/flush/cancel |
| mutex、spinlock、condition、RCU | 保护范围、睡眠约束、同步和可见性 |
| socket/IPC | 协议/地址、通信模式、队列/背压、连接与错误处理 |
| signal | handler 限制、受控退出、回收关系 |
| IRQ、DMA、设备树/ACPI | 硬件边界、DMA 生命周期、匹配和平台配置 |

需要外部机制资料时使用匹配版本的官方文档，并区分通用语义与项目源码事实；实现级细节留给 SDD 或专题分析。

## 5. 选择并核查架构图

使用 Mermaid，图与正文统一模块 ID。完整 SAD 通常提供系统上下文图；其他图按实际复杂度选择，不机械生成固定数量。

- 上下文、组件依赖、数据流、线程/同步拓扑：通常使用 `flowchart`，不要强制层次化。
- 跨组件初始化/关闭、业务流程：使用 `flowchart`；存在明确时序证据时可用 `sequenceDiagram`。
- 错误恢复图仅在代码有相关分支时绘制；`stateDiagram-v2` 仅用于可验证的状态迁移。
- 每条边标明调用、依赖、数据或事件语义，关联正文中的证据/流程 ID；假设和建议明确标记，并与已实现图分开。
- 每图附简短图例、配置条件、证据依据和省略范围。异步注册/提交不能画成即时调用；不默认 `main()` 是入口，内核代码可能由 module_init、probe 或回调进入。

## 6. 独立记录架构风险与建议

围绕已见证据审视职责交叉、耦合/循环依赖、入口集中、私有状态跨界访问、全局共享状态、OS/硬件耦合、接口稳定性、资源与退出约束、同步顺序、错误传播/恢复及配置/日志契约。

每个有依据的候选风险包含：**ID、观察与位置、成立条件、架构影响/可能后果、证据等级、建议/待验证项**。不预设任何风险存在；“入口集中”等特征本身不等于缺陷。

区分观察、条件性风险和已有验证证据支持的缺陷。没有充分证据时写“当前范围未发现充分证据”，不能保证绝对不存在。需要新作缺陷定性时仅列进一步审查入口，不自行生成审查结论或假定 `kernel-code-review` 可用。建议标为 `[建议方案]`，不得写成已经实施。

## 7. 写作、追踪与验证

创建或更新前读取 [SAD 结构与证据表模板](references/sad-template.md)，优先使用项目模板，按范围裁剪主题。模块级请求只交付聚焦内容，不扩张成完整项目文档。

存在 SRS 时建立可验证链：**需求 ID → 架构模块/组件 → 接口 → 源文件/关键函数 → 验证证据（如有）**。缺少 SRS 时只建立“观察到的功能 → 实现位置”索引，说明不是正式需求追踪；无测试记录不声称需求已验证。

交付前检查：

- 基线、目标构建、配置及实际扫描覆盖范围可识别，排除和未知项可见。
- 核心结论、接口、流程、风险均可定位；已有证据 ID/交叉引用未破坏。
- 图、表、文字及源代码一致，无虚构模块、线程、恢复路径或状态转换。
- 主要控制/数据流及正常/异常生命周期有证据，事实、意图、推断、风险与建议分开。
- 读取过引用位置并核对真实行号和成立条件；Markdown 表格/链接/围栏完整。可用时使用现有 Mermaid 工具解析或渲染；工具不可用时做文本检查并说明未渲染，不自动安装依赖或执行项目脚本。
- 复核最终文档 Diff，保留有效既有内容；修改仅限目标 SAD，无额外源码、配置或测试变化。

最终答复给出文档路径（评审则给结果）、覆盖范围、主要结论、实际检查方式及剩余证据缺口。生成了文档不等于架构经动态验证，不声称未执行的构建、测试或渲染已通过。

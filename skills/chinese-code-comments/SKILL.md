# 中文代码注释规范

让维护者理解意图、契约、边界和约束。以当前可见源码为依据，注释量与实现复杂性相称，不用大段注释重复显然代码。

## 1. 范围与不变量

- 先确认用户要求新增、完善、翻译还是审查，以及目标文件/符号；已有明确范围时直接工作，不扩张成全仓库注释改写。
- 阅读适用项目规则、现有注释语言、代码格式和文档工具约定。默认新增说明性注释使用简体中文；项目明确要求其他语言时遵循适用约定，必要时说明与请求的冲突。
- 仅审查时输出问题与建议，不擅自修改。修改模式只处理相关注释，保留用户已有改动，不顺带改代码、命名、include/函数顺序、格式、错误处理、日志或配置。
- 保留 API、符号、寄存器、协议字段及 Linux/POSIX 术语原文，不翻译标识符，不改字符串、打印输出和测试期望来实现“中文化”。
- 保留 SPDX/版权/许可证、第三方来源、必要署名及机器识别的注释指令。生成文件优先查生成源，不擅自修改生成物或将第三方代码全量翻译。
- 文档注释可能参与工具行为。不要改动编译器指令、go:build/go:generate、cgo preamble、lint/type-check/coverage 标记、代码生成标签或其他具有语义的注释，除非任务明确授权且已核查影响。
- Python docstring、Rust doc test 等不能一概视为无运行/测试影响的普通注释；新增/改写前核查项目约定与工具使用，不用 docstring 替换普通注释来绕过边界。
- 不自动提交或推送，不因注释任务启动硬件、装卸模块或执行系统诊断。

## 2. 先核实源码，再写断言

使用限定范围的 `rg` 定位定义、声明、调用方、赋值与错误分支，再读取上下文。需要时追踪配置、宏/内联、回调绑定、初始化/退出和相关测试，不把函数名、旧注释或搜索结果当作实现证据。

重点核对：

- 参数有效范围、NULL 处理、输入/输出方向、长度/单位和返回值。
- 对象创建、发布、引用、借用、所有权转移、有效期及释放责任。
- 执行上下文、锁保护对象、调用方持锁要求、是否可能睡眠和异步停止条件。
- 状态转换、顺序依赖、异常回退、提前返回及适用配置。

注释只能断言足够证据支持的契约。间接调用的目标、运行时状态或外部约束未确认时，降低表述到已知边界或暂不添加，向用户报告待确认项；不要把猜测、候选缺陷或“尚未从源码确认”的长分析塞进正式代码注释。

“意图/原因”须有代码约束或可靠设计资料支持。只能观察到操作时说明操作的约束，不编造历史动机；不把现有宽松实现擅自升级为调用方必须遵守的新契约。

## 3. 内容与位置

- 注释优先解释 **为什么、何时、由谁负责、必须满足什么**，而非逐句翻译赋值、循环或函数名。
- 函数说明描述整体契约；复杂分支前说明特殊条件/原因；资源清理或同步点说明关键顺序约束。注释贴近对象，避免在文件头堆积全部函数实现说明。
- 简单 getter/setter、薄包装和显然局部变量可以不注释；用户明确要求逐行讲解时，优先澄清是否需要单独讲解文档，不自动把源码改成教程。
- 文件级注释仅在有帮助时说明职责、边界与关键约束，不维护容易失真的函数清单、版本历史或未经要求的作者/日期。
- 结构体/枚举/全局状态说明语义、单位、有效值、初始化/销毁、所有权与并发访问规则，避免只复述字段名。宏说明参数求值、上下文或单位等非显然约束，不凭惯例猜测。
- 保留有价值的英文原意；翻译时核对当前实现，修正相关过时内容，不把“翻译”变成额外设计承诺。避免双语重复维护，项目要求双语时例外。
- 使用短句和具体对象，避免“处理相关逻辑”“确保绝对安全”“线程安全”等无边界结论。TODO/FIXME 只在确有依据且任务需要时新增，不把未确认疑点写成已证实缺陷。
- 不嵌入大段调用链、源码行号或易失效的外部分析；必要时引用稳定接口/项目文档，详细推导留给分析文档。

## 4. 格式与 KernelDoc

各语言使用原生注释语法并遵循项目风格。C/C++ 普通实现注释默认 `/* ... */`，多行按现有缩进和行宽；`/** ... */` 仅用于正式文档注释，不把所有注释都升级为 KernelDoc/Doxygen。

Linux 内核/驱动代码按需使用 KernelDoc：

- 适用于公共接口、复杂内部函数和重要 struct/enum；简单 static 函数不强套完整模板。
- 名称/原型与真实声明一致，参数 `@name`、成员、返回和错误码必须准确；不虚构参数，无参数函数不列参数，void 可省略 `Return:`。
- 按相关性记录 NULL、长度/单位、所有权、生命周期、调用上下文、睡眠限制和调用方锁要求，不机械填写未知项。
- 公共 API 通常在公开头文件记录，内部 static 函数在实现文件；遵循现有布局，避免 `.h` 与 `.c` 维护重复契约。
- `Context:` 和 `Return:` 等工具识别字段保留英文标记，说明内容可用中文。类型/成员和标记语法须匹配项目内核版本及实际文档工具。
- 不根据函数内部一次分配/加锁就推定所有调用上下文或线程安全；不要把注册、调度描述成回调已同步执行。

需要格式示例或遇到敏感边界时读取 [注释示例与编辑注意事项](references/comment-examples.md)。示例只示范表达，不能复制其契约到无关接口。

## 5. 编辑与验证

1. 检查工作区和相关 Diff，理解用户已有修改；只编辑目标注释，避免整文件格式化。
2. 逐项复核新增描述与定义、调用、分支、资源/锁操作一致；发现独立功能问题单独报告，不在注释任务里修复。
3. 检查最终 Diff，确认没有代码 token、宏续行、字符串、指令、日志或工具语义变化。注释定界符、行拼接、预处理位置和字符编码须有效。
4. 运行适用的差异/空白检查；已有 KernelDoc/Doxygen 等检查工具可用时检查相关范围，不自动安装依赖。必要时做语法/编译检查，但不为普通低影响注释改动机械新增测试或运行目标。
5. 不用正则删除注释后的文本相等来证明行为不变；这种方法不能可靠处理字符串、预处理、docstring 和工具指令。静态 Diff 复核、工具校验与构建结果分别说明。

通常不需要行为测试，但注释换行可能影响 `__LINE__`、调试行表、生成文档/测试或其他源码位置敏感机制；遇到这些机制时检查具体影响，不宣称二进制完全一致。无法确认影响时缩小修改或说明限制。

## 6. 交付

简要说明修改的文件与注释类型、实际执行的检查、未确认约束及独立发现的问题。只有复核后才能说明“本次仅修改注释”；不把未运行的构建/文档生成/测试写成通过。

未获源码或关键依赖时，可给出规范建议，明确无法生成可靠的项目契约注释，并索取必要路径/文件；不得凭常见内核知识编造注释。
